# XeroWA Product Operating Context

## Product Mission

XeroWA is a production-grade, multi-tenant WhatsApp receptionist and lead-conversion platform for Indian SMBs. It handles approved replies, qualification, appointments, reminders, follow-ups, broadcasts, and owner handoff.

The immediate goal is to move from pre-production evidence to a real Client #1 production loop with observed WhatsApp and database proof.

## Product Boundary

- XeroWA is not the standalone X7 RealEstate product.
- Never import, call, or recreate X7 property-management, colony, resident, society-maintenance, property-finance, property-content, Remotion, or X7-specific advertising services.
- `real_estate` remains a supported XeroWA tenant category.
- Preserve tenant-scoped property inquiry, budget, location, property type, timeline, loan-readiness, site-visit appointment, reminder, follow-up, and owner-handoff behavior.
- Generic campaigns, broadcasts, templates, knowledge, media, appointments, and content drafts belong to XeroWA.

## Supported Runtime

Only these agent services belong to the current XeroWA runtime:

- `xerowa-sales-agent` on port `8080`
- `xerowa-tool-gateway` on port `8081`
- `xerowa-summoner` on port `8082`

Summoner owns WhatsApp ingress, tenant resolution, approved playbook selection, routing, queues, and cron fan-out. Tool Gateway owns controlled external side effects. Supabase is the system of record.

## Supervised Agent Mode

Hermes may autonomously inspect, analyze, test, draft, recommend, create internal tasks, and prepare source changes on a review branch.

Explicit founder approval is required before:

- sending customer-facing messages or broadcasts
- production deployment or alias changes
- applying database migrations or changing RLS/auth
- billing, pricing, refund, or payment changes
- rotating or exposing secrets
- deleting production/customer data
- merging a pull request

Never place raw production secrets in prompts, memory, committed files, or logs.

## Working Rules

1. Start with repository path, branch, remote, HEAD, and `git status --short`.
2. Preserve all user-owned uncommitted files. Never reset, delete, or overwrite unrelated work.
3. Work on `codex/` or another explicit review branch; do not work directly on `main`.
4. Load only the skills needed for the current task. Prefer:
   - `codebase-inspection` for repository mapping
   - `plan` for bounded implementation plans
   - `test-driven-development` for product changes
   - `systematic-debugging` for failures
   - `launch-readiness-audit` for production proof
   - `github-pr-workflow` and `requesting-code-review` for review delivery
   - supervised AI operations skills for risk and approval boundaries
5. Source completion is not production proof. Report source, deployment, and live runtime evidence separately.
6. Before declaring production-ready, require tenant-scoped proof of:
   - business setup and approved playbook
   - signed Meta webhook routing via `phone_number_id -> business_channels`
   - inbound message persistence
   - approved reply delivery
   - qualification and lead persistence
   - appointment/reminder or owner-handoff behavior
   - dashboard visibility
   - no cross-tenant data leakage
7. Historical X7 database fields and migrations are compatibility debt. Remove them only through a separately reviewed, compatibility-safe migration.
